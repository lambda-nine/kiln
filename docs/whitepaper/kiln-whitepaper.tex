\large White paper}
\author{Stephen Estrada}
\date{October 2026}

\begin{abstract}
\noindent AI agents run code as a long series of short tool calls: a shell
command, a test run, a script the model just wrote. Each call is untrusted, each
one blocks the agent, and between calls the sandbox sits idle. kiln is a Linux
container runtime built for that pattern. In randomized measurements across
one ARM Lima VM, an idle-gap sweep showed why an absolute ``cold-start'' number
is misleading: after 5\,s idle, kiln and bare crun converged at
\Vone{v2/gap/kiln-none/g5000/session-p50/median} and
\Vone{v2/gap/crun-none/g5000/session-p50/median}\,ms, while Docker took
\Vone{v2/gap/docker-none/g5000/session-p50/median}\,ms. In a separate campaign
across five fresh boots at a defined 100\,ms gap, the geometric mean of the
per-boot Docker/kiln non-networked one-shot \code{true} lifecycle median ratios
was \Vone{v2/latency/ratio/docker-none/g100/geomean}$\times$ (95\%
session-bootstrap interval \Vone{v2/latency/ratio/docker-none/g100/ci-low}--\Vone{v2/latency/ratio/docker-none/g100/ci-high}$\times$).
A fit over 0--100 idle sandboxes estimated kiln at
\Vone{v2/memory/kiln-none/slope-median}\,KiB per sandbox against
\Vone{v2/memory/docker-none/slope-median}\,KiB for Docker. Across three boots,
Docker's ratio narrowed from
\Vone{v2/workload/shell/ratio/docker-shell/g100/geomean}$\times$ for a tiny
shell workload to \Vone{v2/workload/http/ratio/docker-http/g1000/geomean}$\times$
for an HTTP GET, as fixed overhead was amortized. Non-networked starts need no
shared daemon. kiln provides a user namespace, seccomp, a per-sandbox
disk quota and optional egress policy by default. These are product-level
comparisons of the tested stacks, not component benchmarks; \code{true} measures
runtime overhead, not end-to-end agent speed. kiln is experimental defense in
depth for a trusted operator, not a hostile multi-tenant boundary: sandboxes
share the host kernel and one host UID/GID range.
\end{abstract}

\section{The problem: agents pay the overhead on every step}

An agent works in a loop: the model decides on an action, a tool runs it, the
result goes back to the model, and the model decides again. Tools that touch the
system (run a command, install a package, execute generated code) need a
sandbox, because the code was written by a model or downloaded from somewhere
nobody checked. Three properties of this workload decide what a sandbox runtime
should optimize:

\begin{enumerate}
\item \textbf{Latency multiplies by the number of steps.} The loop blocks on
every tool call, so whatever the runtime adds is paid per step, not per session.
For illustration only: over 50 tool calls, the measured runtime overhead of
\code{docker exec} accumulates to 50 $\times$ \ms{warm/exec-docker/p50}
$\approx$ 2.7\,s, and that of \code{kiln exec} to 50 $\times$
\ms{warm/exec-kiln/p50} $\approx$ 0.18\,s. That is accumulated overhead, not the
end-to-end time of the task, which also includes the model and the commands.
\item \textbf{Sandboxes are mostly idle.} Between calls the model is thinking,
often for seconds. What a sandbox costs while idle, times the number of
concurrent sessions, is what a host pays.
\item \textbf{The code is untrusted.} Isolation has to be the default, not a
flag someone remembers, and it should not have to be traded for latency.
\end{enumerate}

How fast the code runs once started should not depend on the runtime: a
container is a set of kernel features around ordinary processes, so a workload
runs on the same kernel whichever runtime set it up. The CPU microbenchmark
observed no difference; the I/O one was inconclusive (\S\ref{sec:steady}). A
runtime's lever is the cost around the code: starting, idling, running the next
command and tearing down.

General-purpose runtimes are built for long-running services managed by people
and orchestrators, and their costs follow from that (Figure~\ref{fig:paths}).

\textbf{Daemon layers.} \code{docker run} goes from the CLI to \code{dockerd}
over its API, to \code{containerd}, to a per-container shim, and finally to runc,
which does the actual work. Those layers buy remote management, logging
drivers, restart policies and a stable API, none of which a sandbox for one tool
call uses. They show up in the 5\,s-idle one-shot lifecycle
(\Vone{v2/gap/docker-none/g5000/session-p50/median}\,ms for Docker against
\Vone{v2/gap/runc-none/g5000/session-p50/median}\,ms for runc, which Docker uses underneath, though
Docker also prepares an overlay snapshot and a seccomp profile, so the gap is
not the daemons' alone), as resident
memory (\code{dockerd} and \code{containerd} together use about
\V{idle-run1/docker-daemons-pss-mib}\,MiB PSS whether one container runs or
none), and as about 11\,MiB of private memory per container for its Go shim
and PID~1 together (\V{idle-run1/one/docker/uss}\,KiB USS).

\textbf{Generic image handling.} Docker and containerd manage OCI images:
content-addressed layers, snapshotters, registries. That machinery exists to
distribute images between machines. An agent sandbox starts from one image that
is already on the host, so kiln uses that image directly as the read-only lower
layer of an overlay, with a per-sandbox writable layer on top.

\textbf{Joining from outside.} To run another command in an existing container,
\code{runc exec} and \code{crun exec} start a new host process that enters the
container's namespaces one by one with \code{setns}, joins its cgroup, sets
capabilities and seccomp, and only then executes the command. runc, a Go
program, joins the cgroup by writing to \code{cgroup.procs}, which migrates a
running process and waits for an RCU grace period; crun creates the process
inside the cgroup with \code{clone3}. Docker adds its daemon path on top of runc.

\textbf{Grace periods on the critical path.} Making the kernel's RCU grace
periods expedited, a host-wide setting, cut runc's cold start from
\ms{rcu/0/runc-none/p50} to \ms{rcu/1/runc-none/p50} and kiln's former build's
from \ms{rcu/0/kiln-before-none/p50} to \ms{rcu/1/kiln-before-none/p50}: both
were waiting for grace periods. Current kiln and crun are unaffected
(\ms{rcu/0/kiln-now-none/p50} vs \ms{rcu/1/kiln-now-none/p50}; crun
\ms{rcu/0/crun-none/p50} vs \ms{rcu/1/crun-none/p50}).

\section{Design choices that buy speed}

\textbf{No mandatory shared daemon.} \code{kiln run} is one process that sets
up the sandbox, waits for it and removes it. All state lives in the kernel and a
few directories, named by a run ID. A non-networked start needs no shared
daemon; networked sandboxes use kiln-dns, a small fixed service, for DNS. A
persistent sandbox (\code{kiln create}) gets a
small supervisor of its own, a shim, which owns its cleanup; the shim and the
sandbox's PID 1 run the same binary and share almost all their pages, so the
two together cost \V{idle-run1/one/kiln/uss}\,KiB of private memory
(USS) against Docker's \V{idle-run1/one/docker/uss}\,KiB for its shim and PID 1.

\textbf{Born in the cgroup.} kiln creates the sandbox with
\code{clone3(CLONE\us{}INTO\us{}CGROUP)}, so the child exists inside its cgroup from
its first instruction and no running process is ever migrated. The older
approach, writing the PID to \code{cgroup.procs}, cost 5--15\,ms of grace-period
waiting on every cold start and was the largest single step in kiln's own
before-and-after (Figure~\ref{fig:steps}).

\textbf{Talking to the kernel directly.} Starting a helper program costs
milliseconds before it does anything: a cold \code{nft} takes 3.9\,ms just to
load its libraries. kiln configures links, addresses and routes with its own
rtnetlink client instead of \code{ip} and \code{nsenter}, runs exactly one
\code{nft} per networked start (its policy batch ends with a listing that is
checked against the shared base ruleset, and repairs are committed only on
drift), sends teardown deletions as one nfnetlink batch whose socket is closed
by a short-lived child so kiln does not wait for the kernel's deferred
freeing, and leaves the host end of the veth pair to the dying network
namespace.

\textbf{Exec through PID 1.} A persistent sandbox's PID 1 holds a Unix socket,
opened before the sandbox's root was swapped. \code{kiln exec} sends the
arguments and passes redirected stdin, stdout and stderr as file descriptors;
terminal descriptors are refused until kiln has a controlled PTY mode. PID 1
forks the command onto the descriptors and returns its exit code. The command is born with
every namespace, the cgroup, the seccomp filter and the Landlock policy, because
it inherits them. Nothing joins from outside, so there is nothing to re-apply.

\textbf{Security on by default, inside the measured time.} Every number in this
paper includes what kiln sets up by default and the others, as benchmarked, did
not (Table~\ref{tab:setup}): a user namespace that makes sandbox root an
unprivileged host UID, a seccomp filter with \code{no\us{}new\us{}privs}, a
per-sandbox XFS disk quota, and an init process that forwards signals and reaps
orphans. Networked sandboxes get an nftables egress policy (no private ranges
with \code{--net full}; only listed destinations with \code{--allow}) and a DNS
forwarder that resolves only allowed names. A Landlock read-only mode is
available as an option; it was not part of the benchmark runs.

\section{Results}
\label{sec:results}

\textbf{Method.} The v2 harness times direct argument vectors from immediately
before \code{Popen} until \code{waitpid}: setup, the command and the runtime's
synchronous cleanup through CLI exit. Kernel-deferred destruction, such as a
veth tied to a dying namespace, can finish after the timer. Output goes to
files, not pipes. Each measured
round runs every case once; seeded randomized Latin squares balance each case's
position. Ten warm-up rounds precede 100 measured rounds. Five fresh VM boots
are the replication units, and the 95\% intervals below bootstrap the geometric
mean of per-boot median ratios. Individual-invocation p95 and p99 values are not
confidence intervals.

Every runtime starts the same imported Alpine tree under 512\,MiB memory with
no swap, 1 CPU and 128 PIDs. The image is already local. \code{true} is an
overhead microbenchmark: it does no useful work and therefore exposes the
fixed lifecycle cost. It is not time-to-ready, an image pull, cold caches or
evidence that application code runs faster. The end-user stack tier is kiln,
Docker 29.1.3, Podman 4.9.3 and nerdctl 2.4.1/containerd 2.2.1; runc 1.3.4,
crun 1.14.1 and youki 0.7.0 are a low-level floor handed a prepared OCI bundle;
gVisor runsc is reported separately because it interposes a userspace kernel.

The host was an M2 MacBook Air under normal use. The guest was a Lima
\code{vz} VM with 4 vCPUs and 4\,GiB, Ubuntu 24.04 and Linux 6.8 aarch64. Raw
JSONL, copied configs, executable and rootfs hashes, versions, kernel boot IDs
and environment manifests accompany every run.

\subsection{Replicated ratios at a defined 100\,ms gap}

Across five fresh boots, the geometric mean of the per-boot Docker/kiln
non-networked one-shot \code{true} lifecycle median ratios was
\Vone{v2/latency/ratio/docker-none/g100/geomean}$\times$ (95\% CI
\Vone{v2/latency/ratio/docker-none/g100/ci-low}--\Vone{v2/latency/ratio/docker-none/g100/ci-high}$\times$).
The corresponding Podman-with-crun/kiln and nerdctl/kiln geometric means were
\Vone{v2/latency/ratio/podman-crun-none/g100/geomean}$\times$ and
\Vone{v2/latency/ratio/nerdctl-none/g100/geomean}$\times$. On the networked
paths Docker was \Vone{v2/latency-net/ratio/docker-net/g100/geomean}$\times$
(\Vone{v2/latency-net/ratio/docker-net/g100/ci-low}--\Vone{v2/latency-net/ratio/docker-net/g100/ci-high}$\times$)
and nerdctl \Vone{v2/latency-net/ratio/nerdctl-net/g100/geomean}$\times$ kiln.
The corrected Podman network comparison was
\Vone{v2/podman-net/latency/ratio/podman-crun-net/g100/geomean}$\times$
(\Vone{v2/podman-net/latency/ratio/podman-crun-net/g100/ci-low}--\Vone{v2/podman-net/latency/ratio/podman-crun-net/g100/ci-high}$\times$).

\section{Fairness and limitations}
\label{sec:fair}

\begin{itemize}
\item \textbf{One machine, one VM.} Every number comes from a Lima VM (4 vCPU,
4\,GiB) on an M2 MacBook Air: aarch64, Linux 6.8, Ubuntu 24.04. The Mac was
otherwise in normal use. The primary 100\,ms latency ratios use five fresh boots;
representative workloads use three. The idle-gap sweep, concurrency and memory
slope each use one boot and are exploratory. Nothing was measured on x86-64 or
bare metal, and kiln's author ran the benchmarks.
\item \textbf{End-user stacks, not components.} Table~\ref{tab:setup} lists
what each runtime sets up as configured. kiln, Docker, Podman and nerdctl are
complete user-facing stacks, but their image, overlay, networking, seccomp and
daemon paths still differ. runc, crun and youki receive a prepared bundle and
are only a low-level floor. runsc offers stronger isolation. These comparisons
cannot assign a difference to one component.
\item \textbf{Matched inputs, not identical work.} v2 imports one rootfs tar into
each stack and gives every case 512\,MiB memory with no swap, 1 CPU and 128 PIDs.
kiln additionally creates a user namespace and per-sandbox XFS quota. Storage
paths differ: kiln uses overlayfs on an XFS loop device; image stacks use their
configured snapshotters; bare runtimes use the unpacked ext4 tree. The legacy
warm and optimization series predate v2 and did not give Docker an explicit
no-swap flag.
\item \textbf{No universal ``cold'' number.} Figure~\ref{fig:gap} shows that
latency changes materially between 0, 100 and 1000\,ms idle. The paper therefore
names the gap with every lifecycle result. The five-boot confidence intervals
apply to ratios at 100\,ms, not to the one-boot 5\,s values.
\item \textbf{Sampling limits.} p95 and p99 describe individual invocations.
Only the five-boot latency campaign has a five-session interval; the workload
intervals have three sessions and are coarse. Three concurrency batches and
three memory fits in one boot expose behavior but do not establish host-to-host
capacity or confidence intervals.
\item \textbf{An overhead microbenchmark.} \code{true} isolates the runtime's
cost. The representative shell, Python, Node, filesystem, DNS and HTTP cases add
small real workloads, but they remain synthetic one-shot commands. DNS and HTTP
also include public resolver and Internet variance.
\item \textbf{Runtime coverage.} The suite measured Docker, Podman with crun and
runc, nerdctl/containerd, bare runc, crun and youki, and gVisor runsc. The VM
does not expose \code{/dev/kvm}, so Firecracker and Kata were not runnable; they
remain a separate stronger-isolation tier for a KVM host.
\item \textbf{Scope.} kiln has no OCI image or runtime-spec compatibility, runs
on a single host, and has no orchestrator integration yet. Its isolation is a
shared-kernel container's: a kernel bug reachable through an allowed syscall is
still an escape.
\end{itemize}

\section{Future work}

\begin{itemize}
\item \textbf{Pre-warmed pools.} A daemon that creates sandboxes ahead of time
and hands one out on request would turn a cold start into an exec:
\ms{warm/exec-kiln/p50} in the legacy exec series instead of a full lifecycle.
Networked pool members could have their veth pair and firewall chain prepared
ahead too. This needs the planned daemon and a policy for pool size.
\item \textbf{Smaller steps already measured.} Loading libnftables in-process
instead of starting \code{nft} measured 0.55\,ms to load and 1.2\,ms to apply a
policy, against 4--6\,ms for the process: 3--4\,ms per networked start. Returning
the exit code before teardown would save most of the 5\,ms exit phase, at the
cost of cleanup finishing after \code{kiln run} returns.
\item \textbf{Snapshot and restore} of a prepared sandbox (installed packages,
warm files) so a session can start from where a previous one left off; the
overlay's upper layer already records exactly what a session changed.
\item \textbf{Multiple hosts}: a daemon per node and a Kubernetes operator that
places sandboxes, with the same per-node design.
\item \textbf{Next measurements.} Repeat v2 on the intended Mac Mini and on an
x86-64 bare-metal host; replicate concurrency and memory across boots; match
the storage and overlay path where possible; add package installation, larger
images and long-lived exec-heavy agent traces; and run Firecracker and Kata on
a host that exposes KVM. An independent operator should reproduce at least the
headline campaign. The committed traces reproduce the current analysis. A close
measurement rerun also needs the rootfs tarballs identified by hash in the
manifests; publish them as release artifacts first. The original resolved Lima
instance configuration was not archived, so a byte-for-byte environment replay
is not possible.
\end{itemize}

\section{Conclusion}

A sandbox for agents is judged on the cost around the code: how fast it starts,
how it behaves under many simultaneous calls, and what it costs while it waits.
On one ARM VM, with identical rootfs contents and randomized case order, kiln
tracked bare crun's lifecycle floor while remaining far below the tested Docker,
Podman and nerdctl stacks in lifecycle overhead and marginal idle memory. It did
so while turning on a user namespace, seccomp and a disk quota by default. The
result is architectural evidence, not a universal speed claim: idle state
changes the absolute number, most experiments still need another host, and kiln
shares the host kernel. The raw records and manifests make those boundaries
auditable; exact measurement replication additionally requires the separately
archived rootfs artifacts named by their hashes.
